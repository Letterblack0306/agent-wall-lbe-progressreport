The Problem This Solves

⚠ Core Issue: When a coding agent focuses on implementation, governance documentation gets deprioritized. Intent tracking, PROJECT_INDEX updates, gate state management, and acceptance checkpoints are forgotten or done retroactively — leading to contradictions, stale documentation, and governance drift.
✓ Solution: A dedicated governance subagent runs in parallel with the coding agent. The governance subagent's only job is to maintain governance truth — it never codes, it only documents, validates, and tracks.

Interaction Protocol

T+0
CODING Announces intent: "I need to add a new governed tool to the registry"
T+1
GOVERNANCE Validates against PROJECT_INDEX.md — confirms existing owner, checks mutation boundary, records intent in PROJECT_INTENT_LEDGER.md
T+2
GOVERNANCE Returns: "Intent registered. Owner: LBE audit/rule owner. Boundary: Active implementation intent + affected rule owner. Proceed."
T+3
CODING Implements the governed tool. Writes code, tests, validation.
T+4
CODING Reports: "Implementation complete. Files changed: rules/new_tool.py, tests/test_new_tool.py"
T+5
GOVERNANCE Updates PROJECT_INDEX.md if new structure added. Updates implementation-gates.json with current state. Records completion in PROJECT_INTENT_LEDGER.md. Checks for contradictions.
T+6
GOVERNANCE If slice complete: Creates acceptance checkpoint. Updates CURRENT_STATUS.md. Signals coding agent: "Governance truth updated. Ready for next intent."

Governance Subagent Responsibilities

Pre-Mutation (Before Coding Agent Changes Anything)

1. Intent Registration
Record the coding agent's stated intent in PROJECT_INTENT_LEDGER.md before any mutation occurs.
2. Index Validation
Check PROJECT_INDEX.md — confirm the affected structure is indexed, has an owner, and the mutation is within the declared boundary.
3. Gate State Check
Verify implementation-gates.json allows the requested mutation. Check active slice, status, and rules.
4. Contradiction Scan
Check if the proposed intent contradicts any existing documented decision, locked contract, or canonical source.

Post-Mutation (After Coding Agent Completes Changes)

5. Index Update
If new structure was added, register it in PROJECT_INDEX.md with purpose, owner, supporting contract, and mutation boundary.
6. Gate State Update
Update implementation-gates.json to reflect current machine state. Update slice status if applicable.
7. Status Documentation
Update CURRENT_STATUS.md with human-readable current state. Ensure it matches machine gate.
8. Completion Recording
Record completion in PROJECT_INTENT_LEDGER.md. If slice complete, create acceptance checkpoint in docs/acceptance/.

Continuous Monitoring (Always Running)

9. Contradiction Detection
Continuously scan for contradictions between: canonical sources, locked contracts, machine gate state, documentation, and actual implementation. Flag immediately when found.
10. Document Role Inventory
Maintain DOCUMENT_INTENT_MANIFEST.md — every document must have a declared role, owner, and mutation boundary.
11. Publication Gate
Block any publication/version work unless separately authorized by machine gate and user. Publication is never implicit.

Hard Rules (Non-Negotiable)

RULE 1: UNINDEXED_STRUCTURE = NO_MUTATION
If a new subsystem, adapter, provider, UI, database, integration, or directory is discovered, the governance subagent MUST register its purpose, owner, supporting contract, and mutation boundary in PROJECT_INDEX.md BEFORE the coding agent implements it.
RULE 2: No Parallel Architecture
The governance subagent enforces one active slice at a time. No parallel architecture work. No next phase without PASS on current phase.
RULE 3: Fail Closed
When in doubt, the governance subagent blocks. It does not guess, infer, or assume. If evidence is insufficient, status is INSUFFICIENT_EVIDENCE or BLOCKED.
RULE 4: Coding Agent May Not Silently Change Gate
Only the governance subagent (or explicit user authorization) may change gate state. The coding agent must request gate changes through the governance subagent.
RULE 5: Documentation Is Not Code
The governance subagent NEVER writes code. The coding agent NEVER writes governance documentation (except inline comments). Separation of concerns is absolute.
RULE 6: README Is Not a Release Record
The governance subagent ensures READMEs are not treated as status/release records. Current truth lives in CURRENT_STATUS.md and implementation-gates.json.

Implementation Pattern

How This Works in Practice: 
# Coding Agent Session
coding_agent = Cline  # or Codex, or any selected reasoning agent
coding_agent.focus = "implementation"

# Governance Subagent Session (parallel)
governance_agent = LBE-governance  # dedicated governance process
governance_agent.focus = "documentation and validation"

# Interaction Loop
while active_slice is not complete:
    # 1. Coding agent announces intent
    intent = coding_agent.announce_intent("add governed tool X")
    
    # 2. Governance subagent validates and registers
    governance_agent.register_intent(intent)
    governance_agent.validate_against_index(intent)
    governance_agent.check_gate_state(intent)
    approval = governance_agent.approve_or_block(intent)
    
    if approval.blocked:
        coding_agent.receive_feedback(approval.reason)
        continue
    
    # 3. Coding agent implements
    result = coding_agent.implement(intent)
    
    # 4. Governance subagent updates all artifacts
    governance_agent.update_project_index(result)
    governance_agent.update_gate_state(result)
    governance_agent.update_current_status(result)
    governance_agent.record_completion(intent, result)
    governance_agent.scan_for_contradictions()
    
    # 5. If slice complete, create checkpoint
    if governance_agent.is_slice_complete():
        governance_agent.create_acceptance_checkpoint()

Why This Pattern Matters for LBE

Without Governance Subagent

  • Coding agent forgets to update PROJECT_INDEX
  • Gate state drifts from actual implementation
  • Contradictions accumulate silently
  • Acceptance checkpoints are never created
  • Documentation becomes stale
  • Machine gate becomes unreliable
  • Publication blocked by stale state
  • Final product acceptance never closes

With Governance Subagent

  • PROJECT_INDEX always reflects current structure
  • Gate state matches machine truth
  • Contradictions caught immediately
  • Acceptance checkpoints created at slice end
  • Documentation stays current
  • Machine gate remains authoritative
  • Publication path remains clear
  • Final product acceptance can close
